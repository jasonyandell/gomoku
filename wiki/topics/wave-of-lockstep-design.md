# Wave-of-Lockstep Design — Next Run

Design decision recorded 2026-05-20 by Jason after `az-recipe-160k` (run id
`sppjo3z5`) finished its 5000-epoch run. The hypothesis under test in the next
run is that **per-version uniformity in the self-play buffer is the dominant
training quality lever on a laptop-scale AZ setup** — bigger than buffer size,
bigger than τ tuning, bigger than dirichlet noise tuning.

Cross-refs: [TRAINING_WIKI.md](../../TRAINING_WIKI.md) "Next-run config
sketches" section, [az-at-scale-vs-laptop.md](az-at-scale-vs-laptop.md) for
the diagnosis this run aims to validate or refute.

## Hypothesis

`az-recipe-160k` saw 5 exploration-consolidation arcs in 5000 epochs. The
mechanism we observed (and documented in [az-at-scale-vs-laptop.md](az-at-scale-vs-laptop.md)):

1. Each model version's buffer contribution was small and biased — 8-12
   games of "whatever the worker happened to play" with that version's
   weights
2. That biased per-version slice trained the *next* version, which
   amplified the bias
3. Recovery required the model to randomly explore enough to break the
   feedback loop, then "catch up" via the buffer's older slices

If we instead make every version's buffer contribution **uniform and large**
— same sample size, same coverage chance, every version — the per-version
concentration feedback loop should be broken or substantially weakened. We
should see:

- Fewer / shallower arcs (smoother model_elo trajectory)
- More stable plies_mean (less swing between 5-ply attack regimes and
  60-ply defensive regimes)
- Lower variance in pl/vl across cycles
- Possibly faster convergence per version, since each version's gradient
  is computed against a representative sample

The trade-off is **throughput**: we add a per-wave barrier that the
continuous mode doesn't have. Estimated cost ~30-50% wall-clock overhead
per version, but if each version produces a higher-quality gradient, fewer
versions are needed to reach the same Elo.

## Architecture

```
              wave v starts                          wave v ends
                    |                                     |
                    v                                     v
    worker 0  [game 1][game 2][game 3] ... [game 8][game 9 finishes on v]
    worker 1  [game 1][game 2][game 3] ... [game 8][game 9][g10 finishes on v]
    worker 2  [g 1][game 2]   ... [game 8]
    worker 3  [game 1][game 2][game 3] ... [game 8]
    worker 4  [game 1][game 2]                                ... (slow worker)
    ...                                                                ...
    worker 7  [g 1][g 2]...                                       [game 8 done]
                                                                  |
                                          ALL DONE -> trainer ingests wave v
                                          K=1 SGD step on wave v tile
                                          Publish model v+1
                                          All workers reload v+1
                                          wave v+1 begins
```

**Greedy fill semantics:** when a worker finishes its 8th game and the
wave is not yet complete (other workers still finishing their 8th game),
the worker starts game 9 on model v. When trainer publishes v+1, any
in-flight game continues on v until it terminates (its plies are
attributed to v's tile), then the worker reloads v+1 and starts its 8
games on v+1.

This means each version's tile is **at least** `N*G = 64 games`, and at
most `(2N-1)*G ≈ 120 games` (if all but one worker fills greedily before
the slowest finishes its first 8). In practice we expect ~80-100 games
per tile.

## Property invariants we want to preserve

1. **Every game in tile `v` was generated by exactly model version `v`.**
   (No partial-game attribution; no mid-game weight reloads.)
2. **The trainer never advances `v` until at least 8 games from each of
   the 8 workers are in the buffer for `v`.** This is the barrier.
3. **Workers reload model only at game boundaries**, never mid-game.

## Implementation plan

### 1. Trainer-side barrier (`gomoku/train.py`)

The current ingest waits for `--worker-min-positions` total positions
across all workers. New ingest needs to wait for per-worker completion of
G games for the current version.

Concretely:
- Each worker writes published games to a path encoding the model
  version it used: `outbox/v{version}/worker{wid}/game{seq}.pkl` (or
  similar)
- Trainer scans the `outbox/v{current_version}/` directory and counts
  games per worker
- Barrier condition: `all(games_per_worker[w] >= G for w in workers)`
- When barrier fires: ingest ALL games in `outbox/v{current_version}/`
  (including greedy extras), do K=1 SGD step, publish model v+1
- Trainer can ingest in-progress (workers may publish in batches as they
  go) so the SGD step at barrier-fire-time is fast (most positions
  already in the buffer)

### 2. Worker greedy fill (`gomoku/selfplay_worker.py`)

Replace the current `--gen-once-per-publish` mode (which is "generate
one game per publish event") with a new `--wave-mode` flag:
- Track current model version locally
- Generate G games on that version, write each to
  `outbox/v{version}/worker{wid}/game{seq}.pkl`
- After G games: check if a new model has been published; if not, start
  game G+1 on the SAME model version (write to same path with seq=G+1)
- After each game's completion: re-check for new model publish; if new
  model, reload and reset `seq=0` for the new version

The worker never aborts a game in progress. It only checks for new
model publishes at game boundaries.

### 3. Cell config (`scripts/run_sweep.py`)

New Cell `WL1` (wave-lockstep, first iteration):

```python
"WL1": Cell(
    label="WL1: wave-lockstep, 1.5M buffer",
    size="small",
    sims=400,
    stem_padding=3,
    n_workers=8,
    games_per_batch=8,        # G per worker per wave
    wave_mode=True,           # new flag
    buffer_size=1_500_000,
    sgd_per_position=...,     # set so K=1 SGD step per ~3800-position wave tile
    temperature_initial=1.0,
    temperature_drop_step=30,
    temperature_final=0.1,
    c_puct_init=1.25,
    c_puct_base=19652,
    dirichlet_alpha=0.13,
    dirichlet_weight=0.25,
),
```

### 4. New W&B metrics

For diagnosing wave dynamics:
- `wave/version` (gauge): current model version
- `wave/games_in_tile` (gauge): total games published for current
  version, incl. greedy extras
- `wave/games_per_worker` (histogram): distribution of games-per-worker
  in current tile
- `wave/wait_for_slowest_s` (gauge): time from first-worker-done to
  last-worker-done in current wave
- `wave/total_s` (gauge): wave wall-clock time
- `wave/greedy_extras_count` (gauge): number of games beyond the
  N*G minimum

### 5. Sanity test before full launch

Small smoke run: 50 epochs, 4 workers (so the multi-process logic is
exercised but the run is cheap), wave_mode=True. Check:
- Buffer composition has clean per-version tiles
- Barrier actually waits and doesn't slip
- Greedy extras are written and ingested correctly
- No deadlocks (timeouts on barrier)
- W&B metrics look sane

Then launch the real run.

## Held-back levers (for follow-up runs, NOT this one)

These are independent variables we are deliberately *not* changing in
this run, so we can isolate the per-version-uniformity hypothesis. If
WL1 succeeds, hold them constant. If WL1 needs help, try in this order:

1. **Temperature schedule** — bump τ_initial from 1.0 to 1.25, or extend
   temperature_drop_step from 30 to 40. Targets opening-monoculture if
   that turns out to be a residual problem.
2. **K (SGD steps per wave)** — bump from 1 to 2. Targets undertraining
   if model isn't learning enough per version.
3. **Buffer size** — bump from 1.5M to 5M only if the 1.5M lockstep run still
   shows too-recent buffer distribution. This is now a held-back lever rather
   than part of WL1 because 5M changes the hardware/memory axis too much.
4. **Random opening moves** — Jason explicitly rejected this as a
   gomoku-specific concern (random openings construct flawed games for
   a game where openers are critical). Listed here for completeness, not
   recommended.

## Why we expect this to work

The buffer composition argument from
[az-at-scale-vs-laptop.md](az-at-scale-vs-laptop.md): Google's setup
naturally produces uniform per-version sampling via parallel volume.
Our 8-worker setup does not, in continuous mode. Wave-of-lockstep is the
laptop-scale approximation of that uniformity property.

Specifically, this design fixes item #1 of the three structural
differences from Google-scale AZ. It does NOT fix #2 (game length
distribution) or #3 (restart dynamics) — but #1 was the most cited
cause of the arc behavior we observed in `az-recipe-160k`.

## Throughput expectations

Rough math from the run-end summary:
- Current `az-recipe-160k` late state: ~22-25s/cycle, 8 workers × 8
  games, continuous mode
- Wave-lockstep expectation: ~30-40s/cycle (longest worker's 8 games +
  greedy extras + trainer step), barrier-bound

So ~30-50% wall-clock tax per version. To match `az-recipe-160k`'s
5000-epoch wall time of ~33h, we'd reach ~3500 epochs in the same time.
But if each epoch is "worth more" (better gradient quality from
uniform buffer), 3500 epochs of WL1 may be at the strength of 5000
epochs of `az-recipe-160k`. That's the bet.
