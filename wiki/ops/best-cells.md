Both *at or above* the cool refs; the R-S400 curve doesn't decay. The M5 Max sustains production throughput indefinitely under realistic load. (An earlier "~18% haircut" claim was withdrawn — it came from a non-production tiny/V=64 *CPU/BNNS-worker* shape measured right after a synthetic 14-TFLOP GPU hog, not real training.) Caveat retained: CPU-resident work *may* throttle under extreme GPU load (the Lpwr coupling finding) — relevant only if a future heavy trainer approaches hog-level GPU draw. See [[feedback-heat-soaked-is-production]] and [m5-max-cross-engine-coupling.md](../topics/m5-max-cross-engine-coupling.md).

**Cap-status note on R-TRAIN-TINY-ANE / R-TRAIN-MEDIUM-ANE (RESOLVED 2026-05-23 by L09e'):** these references measure **engine isolation** (Core ML at CPU_AND_NE routing under live training pressure), at the `coreml-isolated` cap. **L09e' resolved the residency question for the existing refs: those workers run on the CPU (BNNS), NOT the ANE** — confirmed by `sample` (hot path `BnnsCpuInferenceOperation`, no `H11ANEServicesThread`) and an independent system GPU monitor (ANE utilization 0%). The "ANE" in these ref names is purely the CPU_AND_NE routing label; **the L09c/L09/L09d cells themselves have no ANE residency.** The win is Core ML's CPU/BNNS path beating torch+MPS-contended workers at tiny/V=64. **Additional caveat (Lpwr finding):** the win is **load-fragile** — saturating the GPU collapses the CPU workers −82% (shared package power envelope), so a heavy production trainer would erase it. See [m5-max-cross-engine-coupling.md](../topics/m5-max-cross-engine-coupling.md) for both findings.

**WHY there was no residency — and that it's now fixable (L09i + L09i-fix, 2026-05-23):** L09i found the cause: `coreml_evaluator.export_model_to_coreml` declared a **symbolic `ct.RangeDim` batch dimension** (coreml_evaluator.py:267); the ANE requires fully static input shapes, so Core ML compiled to CPU/BNNS. L09i-fix swapped it for a single **fixed static batch** and **restored genuine ANE residency** — `sample`-confirmed under the live worker (hot path on `AppleNeuralEngine`, zero BNNS). So the engine-placement is now a *choice*, not a limitation. **But at tiny/V=64 the ANE-resident throughput is not yet a win:** L09i-fix-b (fixed batch 192, ~1.37× padding) measured **7,697.7 aug/s** — below both the CPU/BNNS L09c (10,762.6) and the torch baseline (8,039.1). So the R-TRAIN-TINY-ANE best cell **stays at L09c's CPU/BNNS number**; the ANE-resident path is an open envelope (follow-ups: tighter fixed batch; ANE-under-GPU-load vs the Lpwr collapse; re-open small/medium with real residency), not a current promote. The static-batch export trades a per-eval padding tax (single fixed shape, every call padded up) for full GPU vacancy (best trainer_step + 18 epochs/window the lab has measured). See experiment-ledger 2026-05-23 "L09i + L09i-fix".

**ANE-for-self-play strand CLOSED 2026-05-23 (clean evidence):** with residency now achievable, the full re-map says the ANE offers **no self-play win**. (1) Throughput: reject at tiny (7,698 < torch 8,039) and small (clean batch-96 = 1,834 ≈ CPU/BNNS 1,930, −44% vs torch 3,297) — real ANE residency roughly ties the CPU/BNNS path and loses to torch. (2) Contention: L09i-fix-load-v2 (clean pure-self-play A/B) shows ANE workers throttle −35% under a GPU hog (NOT contention-immune), with bidirectional package-power coupling (busy workers cut the hog ~11→2.7 TFLOP/s). So these R-TRAIN-*-ANE refs stay as historical envelope datapoints; the residency capability lives on branch `feat/perf-L09i-fix` (opt-in `--coreml-static-batch`, unmerged) for GPU-IDLE use only (deployment / paced match-eval sidecar). The earlier "ANE −96% / contention-immunity falsified" reading was a wave-barrier trainer-stall artifact — superseded by the clean v2 −35%.

## R-EVAL-* — eval-path latency (ms/move)

CPU/numpy, single process. Behavior-identical promotes only (move selection byte-for-byte pinned).
